# Phase 6 — Images and documents

**Status:** planned · **Design refs:** [§6](../design.md#6-enrichment-pipeline) (image and document
jobs), [§11](../design.md#11-operations) (content addressing, mirror), [H1/J4](../open-questions.md)
**Depends on:** phase 2 (04 for remote intake in practice) · **Gate:**
[S6](spikes.md#s6--pdf-text-extraction-in-pure-go) · **Est:** a weekend

## Goal

Blobs become first-class: photos, screenshots, pasted images, PDFs, and arbitrary files are stored
content-addressed, described by a vision model, made searchable by their contents, and mirrored to
R2. Memory stays flat because every path streams and every decode is bounded.

The two directions matter and are both exercised here: remote saves arrive via R2, in-app saves write
locally and mirror up. The same image arriving from Telegram and pasted in the app must be stored
exactly once.

## Scope

In: content addressing (`data/media/<sha[0:2]>/<sha>`), streaming sha256, thumbnails (max 1600 px),
vision call (kind/tags/OCR/description/colours), embedding of OCR + description, PDF text extraction
+ scan detection + capped OCR, document storage, mirror-up worker, storage reporting, upload caps.

Out: audio transcription, video frame extraction, image editing, HEIC conversion (record as
unsupported and fail with a clear message), archive rendering of PDFs (phase 11).

## Deliverables

```

  hash.go         streaming sha256 (never buffers the file)
  thumb.go        DecodeConfig bounds → thumbnail ≤1600px, EXIF orientation, JPEG/PNG/WebP
  mirror.go       background upload of rows with empty r2_key, retrying, never blocking
  probe.go        dimensions, content type sniffing (http.DetectContentType + extension fallback)

server/internal/enrich/

  document.go     PDF → text → classify/tag/embed; scan → capped OCR
```

## Storage rules (from design.md §11, restated as build rules)

- **Write once, then never mutate.** `incoming/<tmp>` → hash computed while streaming → if a file with
  that sha exists, discard the temp and reuse; otherwise `rename` into `media/<sha[0:2]>/<sha>`.
  fsync the file and the directory before recording the row.
- **Originals are irreplaceable; thumbnails are derived.** Thumbnails live at
  `media/<sha[0:2]>/<sha>.thumb.jpg` and can be regenerated by a task.
- **No filename in the path.** The original filename lives in the DB only (path traversal becomes
  structurally impossible, and `FuzzMediaKey` proves it).
- **Mirror is idempotent and retrying.** `media.r2_key = ''` means "needs mirroring"; the loop picks
  up a batch, uploads, fills the key. Failure increments a counter, never fails the item.

## Tests first

1. `FuzzMediaKey` — arbitrary sha-like strings cannot escape the media root; NUL, `..`, absolute paths,
   unicode separators are all rejected or normalised.
2. Content addressing: the same bytes written twice produce one file and one `media` row (or two rows
   pointing at one file — **decide: one row per item-media relationship, one file per sha**); the hash
   equals `sha256sum`.
3. Streaming hash: a 25 MB file is hashed with RSS growth <5 MB (assert via a generated reader that
   tracks read size, not a real RSS probe in CI).
4. Thumbnail: a 6000×4000 JPEG produces a ≤1600 px long edge image, orientation applied, and peak
   memory bounded (decode into a scaled image, not full decode then scale — measure on the potato and
   record).
5. A corrupt image fails the job with a typed error and the original is still stored (a broken file is
   still the user's file).
6. Vision: recorded fixtures for a screenshot, a photo, a receipt (OCR text), and a diagram; kind,
   3–6 tags, non-empty description, colour list shape. Malformed model output → retry → failed, never
   a half-written row.
7. **Remote/local convergence:** the same bytes ingested via Telegram (R2 intake) and via the composer
   (local) end as one file, two `media` rows if attached to two items, and the mirror-up task uploads
   nothing for the remote one (key already set).
8. PDF: the S6 verdict's chosen library on a text PDF extracts searchable text; a scan yields a
   ratio below the threshold, triggers capped OCR (page cap honoured — assert the vision fake is
   called exactly `min(pages, cap)` times); a malformed PDF is a typed error within the timeout.
9. PDF text hits FTS and the embedding input (search a phrase from page 7).
10. Mirror: a failed upload leaves `r2_key=''` and the item usable; the next tick retries; a success
    sets the key and never re-uploads.
11. `GET /media/<sha>` serves with the right content type, supports `Range`, and refuses a key that is
    not 64 hex chars.

## Exit criteria

Automated: fuzz keys + PDF + media tests green; convergence test green; vision fixtures green;
`make check` green.

Demo:

1. Send a photo to the bot → item appears, thumbnail correct, description plausible, OCR text present
   when the photo contains text.
2. Paste the *same* photo into the composer → one file on disk (`sha256sum` matches both), no duplicate
   storage, no second vision call (hash dedupe) — assert by checking the usage log.
3. Upload a 20 MB text PDF → extracted text searchable; a page-7 phrase finds the item.
4. Upload a 30-page scan → OCR capped at 10 pages, `pdf_text_state='ocr'`, first pages searchable.
5. Upload a corrupt `.png` → item exists, thumbnail placeholder, amber strip, retry fails cleanly.
6. Block egress; save an image in the app → it works, `mirror_pending` increments; unblock; it drains.
7. Disk number in Settings matches `du -sh data/media` (within rounding) and the warning fires at the
   configured threshold.
8. `docker stats` peak during a 20 MB PDF + a 25 MB image: record RSS; must stay under the budget.

## Risks

- **Peak RSS is the whole risk of this phase.** A 25 MB JPEG decoded at full size is 100 MP of RGBA.
  Use `image.DecodeConfig` + a bounded decoder; never `image.Decode` a user file without a pixel cap.
  Write the pixel cap down and test it.
- **A hash mismatch between paths** would silently duplicate storage. The convergence test is the
  guard; keep it.
- **PDF bombs.** Page count, per-page time, total time, and memory all need caps; the S6 numbers set
  them.
- **Mobile photo orientation.** EXIF handling is the difference between a library that looks right and
  one that looks broken; test with a real iPhone photo, not a synthetic one.
- **R2 presign vs direct proxy for blobs.** The design says the browser fetches from R2 via presign;
  for local originals it fetches from the potato. Both paths must be tested, and the item page must
  not flicker between them.
- **Mirroring is never allowed to block.** If the mirror loop wedges, saves must still work; the
  `mirror_pending` count is how a wedge becomes visible.

## Build-time decisions to record

- One `media` row per item attachment vs one per blob (recommend per attachment, with the file shared
  by sha).
- The pixel cap for decode (recommend 50 MP) and the thumbnail method (scale-on-decode).
- `pdf_text_state` values and the scan threshold default.
- Whether an unsupported image format (HEIC) is rejected at intake or stored and left undescribed
  (recommend: stored, described by nothing, a clear badge — never lose the file).
